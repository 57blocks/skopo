# Agent 写代码，我们写什么？

*认识 Skopo*

草稿 · 2026-10-28 · 对应规范：Skopo Specification 0.1.0（草案，尚未发布）

## §0 请假 40 小时

有一家公司自己开发了考勤系统。今天（2026 年）的代码里写着这样一条规则：请假超过 40 小时，需要升级到 L3 经理审批。可如果翻开这个系统的 PRD，上面写的却是：请假满 5 天，要过三级审批，依次是项目负责人、L2 经理和 L3 经理。

一位员工周一到周五请了整整 5 天，正好 40 小时。按 PRD 要走三级，按代码只走两级。那么，这是一个藏在边界上的 bug？还是说，我们应该坚持代码才是唯一的 source of truth，PRD 只是没有及时更新？

说它是 bug 当然可以，但真正的问题早就埋在 PRD 那句不够严谨的自然语言里：“满 5 天”，什么叫满？恰好 5 天算不算？天是按日历算，还是按工作时间折算？周五下午请到下周五上午，又算几天？PRD 没说清楚的地方，开发只好自己补上：5 天就是 40 个工作小时，“满”就是“>”。每一步“翻译”单看都说得过去，合起来却引入了一条新规则：恰好 40 小时，不算满 5 天。

这样的分歧，你觉得要多久才会被发现？这份 PRD 最后一次更新是在 2019 年。这七年里，这家公司的 Jira 上累积了 3,700 多个 ticket，代码库里的 commit 和 PR 更是不计其数。“系统应该是什么样”就在这一次次变更里慢慢漂移，到今天，这个问题已经没有人能准确回答。代码能回答“系统现在是什么样”，可除非当初有人肯写详尽的注释和 commit message，它说不清一件事为什么要这么做，更说不清该不该这么做。

而且软件行业正在经历更大的变化：agentic coding 把软件开发推上了一个新的抽象层级。今天的代码越来越像昨天的汇编：它还在，只是人越来越少去读、去改它。到了这一层，人先关心的不再是用 C# 还是 C++、数据放进 SQL 还是 NoSQL，而是系统应该是什么样。那我们要用什么方式来表达自己的意图，又该怎么管理这些表达？这篇文章要介绍的 Skopo，是我们尝试给出的一个回答。

现在假设 HR 确认过，PRD 的本意是：恰好 5 天也要 L3 经理批准。那么按 Skopo 的规矩，这条规则不能照抄 PRD，得先把“天”怎么算说清楚，再用落在边界上的例子把它钉住：

```skopo
spec · spec/leave/approval.md
- **请假时长**按工作时间计：只算工作日里的工作时段，一个工作日 8 小时，周末和法定假日不算。 ^T-1e3wfx
- 请假时长不少于 40 小时的申请，**应**依次经项目负责人、L2 经理和 L3 经理审批。 ^R-wwab73

> *例*：员工从周五下午请到下周五上午：首尾两个半天各 4 小时，中间四个工作日 32 小时，一共 40 小时。申请要过项目负责人、L2 经理和 L3 经理三级。 ^E-jqc9df (R-wwab73, T-1e3wfx)

> *例*：员工请周一到周五，其中周三是法定假日，请假时长是 32 小时。申请不用过 L3 经理。 ^E-cgqyw9 (R-wwab73, T-1e3wfx)
```

第一句先把“请假时长”说死：按工作时间算，不按日历。第二句里加粗的**应**，说明这是一项要求，不是一句描述；“不少于”把“满”的意思也说死了。后面两个例子都在边界上：第一个跨了周末，首尾各半天，加起来正好 40 小时；第二个在日历上是 5 天，按工作时间却只有 32 小时。代码要是用了“超过”，第一个例子就对不上；要是按日历算，第二个就对不上。每句末尾的 `^T-1e3wfx`、`^R-wwab73` 这些，是它们的 ID。

代码可以交给 agent 去读、去写，决定却还得人来做。Skopo 也不能替你把事情定下来，但能帮你把定下来的事情说清楚：一条规则只写在一个地方，只有一个 ID，边界情况有例子；以后要改，就有明确的位置可改，而且要说清楚改的是意思还是措辞。很明显，skopo 里写的都是普通的中文，特别的只是它守着的一套规矩。这也是 Skopo 的核心主张：

> [!QUOTE]
> 不需要一种新语言，只需要一套新规矩。

## §1 Skopo 是什么

Skopo 这个名字和 telescope、microscope 用的是同一个词根，都来自希腊语 σκοπός，意思是“目标、意图”。

本质上，skopo 就是按一套规则编写、组织起来的一组 Markdown 文件，这套规则叫做 Skopo Specification。这些文件我们建议放进一个独立的 repository，叫做 skopository；它们合起来，就是一个系统的 skopo。规范也允许把它放进代码 repo，作为其中的一个 `skopo/` 目录。

用一句话说：skopo 把“系统应该是什么样”写成一条条带编号的自然语言陈述（statement），分三层存放，用加粗的关键词标出哪句是要求，人接受了的版本记在 lock 里。开头那四句话，就是那家公司考勤系统的 skopo 里的四条。

### 1.1 一条 statement 长什么样

一条 statement 就是一个 Markdown 元素，可以是一段话、一个列表项、一个引用块，也可以是表格里的一行。它的末尾有一个 anchor，比如 `^R-wwab73`，这种写法借自 Obsidian 这类笔记工具的块引用。`^` 后面的字母说明这条 statement 是哪一种，一共七种：

| 字母 | 英文 | 是什么 | 在哪一层 |
|---|---|---|---|
| T | term | 词汇：一个词的意思 | spec |
| A | act | 行为：有人做了什么，接着发生什么 | spec |
| R | rule | 规则：要求、禁止或许可什么 | spec |
| W | assumption | 假设：系统依赖、却不负责保证的事实 | spec |
| E | example | 例子：一个具体场景，展示规则让什么成立 | spec |
| F | form decision | 形态决定 | product binding |
| D | design decision | 设计决定 | tech binding |

字母加六位字符合起来是它的 ID，比如 R-wwab73。句子里加粗的**应**表示这是一项要求；anchor 后面括号里的是引用，比如一个例子写明它检查哪几条规则。这几样东西的细节在 §2.1。

> [!FIGURE] fig-statement · 一条 statement 的解剖
> 放大一条 statement：`- 请假时长不少于 40 小时的申请，**应**依次经项目负责人、L2 经理和 L3 经理审批。 ^R-wwab73`。
> 用引线标出：列表项（一个 Markdown 元素）、加粗关键词（强制力）、anchor、kind 字母 R（规则）、六位 key（身份）。
> 下方再放一条完整的例子：`> *例*：员工从周五下午请到下周五上午：首尾两个半天各 4 小时，中间四个工作日 32 小时，一共 40 小时。申请要过项目负责人、L2 经理和 L3 经理三级。 ^E-jqc9df (R-wwab73, T-1e3wfx)`，标出括号里是"这个例子检查的规则"。

### 1.2 一个 skopository 里有什么

打开一个 skopository，顶层是这样的。还是拿那家公司的考勤系统举例：

```
attendance-skopo/
  skopo.json             照的是哪一版规范
  keywords.json          每种语言的加粗关键词
  README.md              这份 skopo 描述什么、怎么读
  spec/                  世界里什么必须为真
    people.md            各领域共用的词：员工、办公室、角色
    leave/
      charter.md         请假这个领域的词汇和原则
      approval.md        申请与审批
      balances.md        假期余额怎么算
    local/
      shanghai.md        上海办公室自己的规定
  bindings/
    product/
      attendance.md      考勤系统的形态决定
    tech/
      attendance.md      考勤系统的设计决定
  rationale/             改动的记录
  views/en/              英文翻译
  spec.lock.json         人接受了的文本和指纹
```

最重要的是 `spec/` 和 `bindings/`，它们把一个系统分成三层来描述：

- **spec**：这个系统所服务的世界里，什么必须为真。“世界”指的是不靠软件也存在的那部分，比如公司的请假制度。spec 按领域分文件夹，§2.2 细说。
- **product binding**：产品的使用者看得到、也依赖的东西，比如有哪些界面、对外的 API 长什么样、通知走什么渠道。这些我们统称为产品的形态。每个产品一份，放在 `bindings/product/` 下。
- **tech binding**：只有产品的实现者，也就是开发者，才看得到的东西，而且停在设计这一层：拆成哪些服务、用什么存储、组件之间怎么通信、谁有权访问什么。每个产品一份，放在 `bindings/tech/` 下，和它的 product binding 同名。

为什么叫 binding？因为同一份 spec 可以绑定成不同的产品：同一套请假制度，可以做成网页，也可以做成一个聊天机器人。两份 binding 记下的，就是这一次具体绑定成了什么样，又是怎么造出来的。再往下才是代码，而代码不在 skopository 里。一条 statement 该放进哪一层，靠层与层之间的几个问题来分，§2.3 细说。

> [!FIGURE] fig-layers · 三层，和分开它们的问题
> 自上而下四个水平带：spec、product binding、tech binding、code。code 画在虚线框里，标"不在 skopository 里"。
> 层与层之间各放一道"门"：spec 和 product binding 之间那道标"外部方会反对？人工加纸笔也成立？"，product binding 和 tech binding 之间标"只有使用者会注意到？"，tech binding 和 code 之间标"代码重写一遍还在？"。
> 右侧画向上的箭头，标"引用只往上指"；画一支从 skopo 指向 code 的箭头，把它划掉，标"skopo 不引用代码"。
> 每一层旁边用一句话写它装什么，用词照搬正文。

剩下几样，管的是变化和读者：

- `spec.lock.json` 是 lock，记下人接受了的每条 statement 的原文和指纹。之后 skopo 和它之间的每一处差异，都得有个交代。
- `rationale/` 放改动的记录。每份记录声明一次改动碰了哪几条、改的是意思还是措辞，愿意的话再写上为什么。lock 和 rationale 怎么配合，§2.4 细说。
- `views/` 只放翻译。员工手册、测试计划这类给特定读者的文档，要的时候从 skopo 生成，不存回来。
- `skopo.json` 写明这份 skopo 照的是哪一版规范，`keywords.json` 列出每种语言的加粗关键词，`README.md` 告诉读者这份 skopo 描述的是什么系统。

### 1.3 和常见的四种文档比

那 skopo 和开发者手边已有的文档有什么不同？拿最常见的四种来比。PRD 回答“要做一个什么产品”，写给业务方和 PM；TRD 回答“打算怎么实现”，写给开发；代码旁的文档，也就是 README、`docs/`、ADR 和 AGENTS.md 这类文件，回答“在这个 repo 里怎么干活、当初为什么这么定”，写给开发者，现在也写给 agent；test case 回答“这个输入应该得到什么输出”，写给 QA 和 CI。skopo 回答的是另一个问题：“这个系统应该是什么样，为什么”。

| | 业务方读得懂 | 说清为什么 | 每一条有身份 | 分得清要求和描述 | 机器能检查 | 世界、形态、设计分开写 | 改了意思看得出来 |
|---|---|---|---|---|---|---|---|
| PRD | ✓ | 看怎么写 | ✗ | ✗ | ✗ | ✗ | ✗ |
| TRD | ✗ | ✓ | ✗ | ✗ | ✗ | ✗ | ✗ |
| 代码旁的文档 | ✗ | 看怎么写 | ✗ | ✗ | ✗ | ✗ | ✗ |
| test case | ✗ | ✗ | ✓ | ✓ | ✓ | ✗ | 看怎么写 |
| skopo | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

> [!FIGURE] fig-spectrum · 开发者手边的文档，和 skopo
> 画成一张矩阵，内容照搬正文的表格：五行（PRD、TRD、代码旁的文档、test case、skopo），七列，列名照搬表头。✓ 画实心点，✗ 画空心点，"看怎么写"画一个短横线。
> 前四行按从业务到代码的顺序排在一条光谱上；skopo 这一行单独放在光谱之外，标"自然语言，加一套规矩"。
> 不要把 skopo 画成光谱上的又一个点。

把这四种文档从业务到代码排开，skopo 并不在这条线上。它想同时拿到两头的好处：像 PRD 一样让业务方读得懂，又像 test case 一样每一条都有身份、分得清哪句是要求、机器能检查，只是它能查的是 skopo 自己的格式、引用和改动声明，不能像测试那样运行；一条 statement 该放哪一层、意思对不对，最后还是靠人判断。表里还有两列，只有 skopo 给它们留了位置：把世界、形态和设计分开来写，以及每次改动都要说清楚意思变没变。

要说明的是，这张表比的是每种文档在设计上给这些东西留没留位置，不是说每一份都做到了。skopo 的几个勾也有前提：写了 rationale record，才说得清为什么；有了 lock、改动也都声明了，才看得出意思变没变。

所以 skopo 不是在旁边多加一份文档，而是把这些文档里最该留下来的那部分接过来：PRD 里讲业务规则的部分进 spec，讲产品形态的部分进 product binding；TRD 里的设计决定进 tech binding；test case 背后那句“应该得到什么”，变成一条条给人读的例子；README 和 AGENTS.md 里“这个系统必须怎样”的那些话，也属于 skopo。

和 skopo 最像的，其实是 BDD 的 Gherkin：业务读得懂，有例子，还能跑。可它在实践里大多滑向了“点哪个按钮、看到什么”的界面步骤，又和测试代码绑在一起，界面一改就得跟着改，最后没人愿意读。skopo 的例子故意不能运行，它停在世界这一层，不写按钮也不写页面。这样它不会被界面拖着走；可如果代码改了、skopo 没改，它一样会过时，这一点 §2.4 末尾会说。

### 1.4 它不是什么

最后，把几个容易混淆的地方说清楚：

- 它**不是一种新语言**。statement 就是普通的中文或英文，只是守着几条规矩。
- 它**不是一个工具，也不绑定哪套流程**。Skopo 是一份规范，我们的插件和检查器只是它的一种实现。规则书规定的是 skopo 长什么样、每次改动要声明什么，以及写 skopo 的工具至少要守住什么；至于它从哪里来、什么时候和代码对照、给谁用，留给团队和工具去定。
- 它**不是写完就扔的前期文档**。skopo 和代码一起演进，我们叫它代码的伴生文档（companion）。我们建议它单独成一个 repo，和代码 repo 并排存放。
- 它**不是另一个 Confluence**。进度、计划、讨论这些东西永远不进 skopo，§2.5 有完整的清单。
- 它**不是代码的索引**。statement 里从不写代码在哪儿：不写源文件路径，也不写模块名和函数名。

想先试再读的话，命令在 §4 末尾：装上 Claude Code 插件，在一个规则多的 repo 里跑 `/skopo:init`，就会得到一份 skopo 草稿和一份问题清单。

## §2 规则的细节

§1 说了 skopo 长什么样，这一节说它守着哪些规矩。例子还是那家公司的考勤系统。

### 2.1 statement：加粗、ID 和引用

**只有加粗的关键词才有强制力。** 中文用 **应**、**不应**、**可**，英文用 **must**、**must not**、**may**，分别表示要求、禁止和许可。只有加粗的才算数，不加粗的句子只是描述。这里故意不设“应该”“建议”这一级：一条规则要么是要求，要么不是。留一个“建议”，模糊就又回来了。

回头看代码里那条规则：“请假超过 40 小时，需要升级到 L3 经理审批。”这里的“需要”，在日常说话里就是要求，可它没有任何标记，工具认不出来，翻译时也可能被译成一句描述。在 skopo 里，lint 会把这种藏在字面里的强制力标出来。这条规矩不是拍脑袋定的。我们第一次用工具自动恢复一个融资平台的 skopo 时，agent 把 284 条规则中的 225 条写成了“会被拒绝”“永远不会”这样的陈述句，意思没错，强制力却丢了。改了写作指南、加了这项 lint 之后，第二次运行时 266 条规则里有 219 条带上了关键词。

**ID 是永久的。** ID 里那六位字符叫 key，是随机生成的，和 statement 在哪个文件、说了什么都无关；一旦分配就不再变，删掉的 key 也不会再给别的 statement 用。所以文件可以拆、可以合、可以挪，引用它的地方都不受影响。字母则跟着层走：一条决定从 product binding 挪到 tech binding，F 就变成 D，key 不变。

**引用只能往上指。** anchor 后面的括号是引用：例子写明它检查哪几条规则，形态决定和设计决定写明它是为哪几条规则做的；一条规则如果是在细化另一条，就写 `refines`。每一层只能引用自己这一层和它上面的层：spec 只引用 spec，product binding 还可以引用 spec，tech binding 三层都可以引用。skopo 从不引用代码，反过来，代码倒是可以引用 skopo。这条规矩是在一次试点里吃过亏之后定下的：那次的 tech binding 一开始写成了一张“每条规则在哪个文件、哪个函数里实现”的索引，结果每次重构都得跟着改 skopo。

### 2.2 spec：按领域组织

spec 按领域分开。每个领域有一份 **charter**，写着这个领域的词汇和几条原则，通常五到七条；下面是若干份 **topic** 文件，每份只讲一件事，比如请假的申请与审批、假期余额怎么算。某个地区或办公室自己的规则放在 `spec/local/` 里，用 `refines` 指向它细化的那条通用规则，在自己的范围内取代它。领域按“一个词在哪里换了意思”来切：在那个融资平台上，approval 在三个地方分别指资料审核、转账审批和授信决定，于是被分成了三个领域。

例子不必每条规则都配，挑在规则容易被读错的地方就好，最好落在边界上，就像开头那两个。

这套组织方式借自法律。法律就是一种用自然语言写成、运转了几百年的“源码”。它从来没打算消除歧义，而是把歧义交给有权决定的人，再把决定记成判例。Skopo 也一样，只是不借法律的文风。

> [!FIGURE] fig-law · 法律和 Skopo 的对应
> 两栏对照，左栏"法律"，右栏"Skopo"，每行一对：条文 ↔ statement；条文编号 ↔ ID；纲领与细则 ↔ charter 与 topic；特别法优于一般法 ↔ refines；修正案 ↔ 一次改动（PR 的 diff 加上 rationale record）；判例 ↔ example；法官 ↔ 有权决定的人，agent 负责把问题交到他手里。
> 中间用细线连接，不画天平、法槌之类的图标。

### 2.3 两种 binding：一条 statement 放哪一层

一条 statement 该放进哪一层？按顺序问自己几个问题：

1. 外部有没有人会反对改它？比如客户、合作方、监管机构，或者某个由外部机构发布的标准。有，就放进 spec。
2. 假如把整个系统换成人工加纸笔，它还成立吗？成立，也放进 spec。
3. 改了它，是不是只有产品的使用者会注意到？外部方不在乎，世界里的规则也没变，只有用这个产品的人会发现，那它是产品的形态，放进 product binding。
4. 改了它，是不是只有产品的实现者，也就是开发者，才会注意到？是的话，再看它是不是设计层面的决定：拆成哪些服务、数据放进什么存储、组件之间怎么通信、谁能访问什么。按同一个设计把代码从头重写一遍，它还在，就放进 tech binding。
5. 代码一重写就会变的，比如函数怎么拆、文件放在哪、变量叫什么，只是代码本身或编码约定，不进 skopository。

放到考勤系统里，三层分别是这样的：

```skopo
spec · spec/leave/approval.md
- 请假时长不少于 40 小时的申请，**应**依次经项目负责人、L2 经理和 L3 经理审批。 ^R-wwab73

product binding · bindings/product/attendance.md
- 员工提交请假申请之前，就能看到这次要经过哪几级审批。 ^F-9zbwzz (R-wwab73)

tech binding · bindings/tech/attendance.md
- 审批路线由一个无状态的规则算出：输入申请人、请假时段和当时的组织架构，输出依次审批的人。 ^D-qp9xff (R-wwab73)
```

“不少于 40 小时要过三级”，就算公司退回到人工加纸笔也照样成立，所以它在 spec。“提交前就能看到审批路线”，改了它，HR 的规定不受影响，只有用系统的员工会发现，所以在 product binding。“审批路线由一个无状态的规则算出”，员工看不到，只有开发者知道；按同一个设计把代码重写一遍，它也还在，所以在 tech binding。

这样分开以后，原来的 PRD 并没有消失，它降成了 product binding 那一薄层，只是不再和世界的规则混在一起。哪天要把请假从网页搬进聊天机器人，动的只是 binding，spec 一个字都不用改。

这几个问题是用来放东西的，不是要求纯粹：抽象总会渗漏。有些规则只在某些形态下才成立，比如“一条消息同时通知很多人时，收件人不应看到彼此的地址”。它可以留在 spec 里，但要用加粗的 **凡采用**（英文是 **Where**）开头，声明它依赖形态。渗漏不禁止，只要声明，就能被数出来。

### 2.4 变更管理

skopo 里的文件就是普通的 Markdown，怎么编辑都可以：用编辑器手改、在 PR 里改，或者让 agent 改。不过我们推荐把具体的编写交给 agent：人说清楚要改什么、看 diff、拍板；措辞、编号、引用、rationale record 和 lint 这些细活，由 agent 来做。

`spec.lock.json` 记下了每条 statement 被人接受时的原文和指纹。之后 skopo 和 lock 之间的每一处差异，都要在一份 rationale record 里声明：改了意思的写进 Touches，只改措辞的写进 Rewords，删掉的写进 Retires，愿意的话再写上出处和理由。没声明的差异过不了 lint。所以规矩只有一条是硬的：任何时候，commit 下来的 skopo 和它的 lock 放在一起跑 lint，都不能有一个 error。改到一半可以对不上，提交的时候必须对得上。

比如 HR 决定把门槛从 40 小时降到 24 小时，也就是从 5 天降到 3 天，这次改动就会带着这样一份记录：

```skopo
rationale · rationale/2026-10-12-l3-from-24-hours.md
# 2026-10-12 · 请假 24 小时起就要过 L3

| | |
|---|---|
| Touches | R-wwab73, E-jqc9df, E-cgqyw9 |
| Sources | HR 例会纪要，2026-10-12 |

3 天以上的缺勤已经开始影响项目排期。
```

改动被接受之后，lock 重写。谁来拍板，由团队自己定，一般就是现实里决定这类事的人：业务规则找业务负责人，设计决定找架构师。lock 只记文本，不记是谁、在哪天接受的，这些交给 git 历史和 PR 去记。

声明为“只改措辞”的改动有没有悄悄改了意思，还可以再让模型查一遍。在一次实验里，我们故意埋下 6 处改了意思的改写，它全部找了出来，另外 23 处意思没变的对照，没有一处误报。不过它只报 warning，最后还是人说了算。

> [!QUOTE]
> 改了意思，就要说出来。

还有一点要说清楚：lock 只看得见 skopo 自己的改动。有人只改了代码、没动 skopo，lock 是看不见的；反过来，skopo 先改了、代码还没跟上，lock 也不会提醒。不管哪边先动，要做的都是同一件事：把代码和 skopo 逐条对照，找出对不上的地方，交给人来定，而不是让工具悄悄把一边改成另一边的样子。开头那个 40 小时的矛盾就是这么找出来的（§3.1）。这种对照该在每次 merge 时做，还是定期做，现在还没定。规则书能保证的是，对照的时候，有一份逐条、带编号、人接受过的文本可以对。

### 2.5 不要放进 skopo 的东西

进度、计划、负责人、会议记录、讨论、调研、问题清单、操作指南和 changelog，这些东西永远不进 skopo。原因不只是人读不过来，就算将来读它的全是 agent，膨胀也会稀释它最值钱的东西：一条条由人拍了板的决定。

秘密、密钥和个人数据也不进 skopo，人名也不写，只写角色。

给特定读者看的文档，比如员工手册、审批矩阵、测试计划，都只是从 skopo 生成的 view：要的时候生成，用完就扔。唯一会存回 skopo 的 view 是翻译，因为译文同样要有人接受。lock 记下了每条译文照着的是原文哪一版，所以原文改了以后，能查出哪些译文落后了；不过目前还得手动去比，工具不会主动提醒。

## §3 使用场景

规则书对写 skopo 的工具有几条最低要求，但不管流程：skopo 从哪里来、什么时候和代码对照、给谁用，我们自己也还在摸索，§4.2 列了还没试过的那些。下面挑三个场景，都是 skopo 做得到、前面那几种文档做不到的。第一个我们做过，后两个还是设想。

### 3.1 给老系统做 reverse engineering

开头那个 40 小时的矛盾，就是在这样一次实验里冒出来的。我们让 agent 读那个考勤系统的代码、2019 年的 PRD 和 commit 历史，再和人一起把“系统应该是什么样”写成一份 skopo。写下来的规则、行为和形态决定一共 104 条，其中 34 条除了代码找不到任何出处，也就是说，代码是它们唯一的记录。同时冒出来 27 个需要人拍板的问题：17 个是代码和早先的文档互相矛盾，6 个是哪份文档都没写到，另外 4 个是措辞和分层上的问题。“恰好 40 小时该走几级”就是其中之一。

为什么非得是 skopo？如果目标是一份新的 PRD，矛盾只能写成一段段说明，没法逐条确认；如果目标是测试，测试只会把代码现在的行为当成对的，“超过 40 小时”会被原样固定下来。skopo 的粒度刚好合适：每个矛盾都落在一条有编号的 statement 上，变成一个具体的问题；人回答之后，这条 statement 就从恢复出来的草稿变成了人做的决定，等人接受了这份 skopo，它就记进 lock。

> [!FIGURE] fig-loop · 一次 reverse engineering
> 左边是 skopo，右边是代码和旧文档。
> 上方一支从代码到 skopo 的箭头，标"读出 statement，找出对不上的地方"。
> 下方一个循环：对不上的地方 → 变成问题 → 人回答（改 skopo、改代码，或者"这不是意图"）→ 接受，记进 lock。
> 人出现在"回答"这一步，用一个简单的标签表示，不画人像。

同样的做法，我们也用参考工具在一个融资平台上全自动地跑过：两个 repo、61.5 万行 TypeScript，34 分钟写出 518 条 statement，列出 66 个问题。

### 3.2 从意图开始一次改动

假设 HR 决定把门槛从 40 小时降到 24 小时。这次改动可以从 skopo 开始：把 R-wwab73 里的 40 小时改成 24 小时，边界上的两个例子跟着挪到新的边界，再附上 §2.4 里那样一份 rationale record。agent 拿着这份 diff 去改代码，PR 里同时带着 skopo 和代码两边的改动。

review 的人先看到的不是两百行代码，而是一行声明：R-wwab73 的意思变了，为什么变。代码的 diff 看不出改的是哪条规则；跟着一起改的测试，只能证明代码和测试一致，证明不了这是不是本意。这其实就是我们设想中 agentic coding 的出发点，§4.3 再说。

### 3.3 审计：这条规则从什么时候开始是这样

在金融、人事、合规这类系统里，迟早会有人问：这条规则从什么时候开始是这样的？为什么？谁拍的板？今天要回答它，得翻 PRD 的历史版本、Jira 和 commit，而且 commit 里重构和规则改动混在一起，很难分清哪次是改了意思。

在 skopo 里，这个问题可以机械地查出来：把 Touches 里列了 R-wwab73 的 rationale record 全找出来，按日期排好，写了出处和理由的一眼就能看到，再加上 git 和 PR 里谁在哪天接受的记录。只改措辞的那几次，因为被声明为 Rewords，不会混进来。前提是每次改动都留了 rationale record，git 的历史也还在；没留记录的改动，只看得到文本变了，看不到为什么。这也还算不上审计级的记录：rationale record 本身没有指纹，事后被改了未必查得出来。

## §4 来历、现状和愿景

### 4.1 来历：前人做过什么

把意图写成既读得懂、又查得了的东西，这件事不新，几十年来很多人试过。它们没能流行开来，多半是因为写和维护的成本太高，而不是表达力不够。Skopo 的规矩几乎每一条都能在前人那里找到出处；把这些零件拼成一个能运转的整体，是我们做的事：

| 要求 | 规矩 | 借自 |
|---|---|---|
| 用词一致 | 每个领域先在 charter 里定词汇，一个词换了意思的地方就是领域的边界 | Domain-Driven Design 的 ubiquitous language 和 bounded context、SBVR |
| 哪句是要求，一眼看得出 | 只有加粗的关键词有强制力，每种语言一份词典 | RFC 2119 / 8174、EARS、GB/T 1.1 |
| 能指着一条说话 | 一个元素一条 statement，key 随机生成、永不改变 | 法律文本把永久身份和位置编号分开（Akoma Ntoso）、StrictDoc 随机生成的 MID |
| 意思不含糊 | 用例子钉住规则 | Specification by Example |
| 不和实现、形态绑在一起 | 三层，引用只往上指 | Jackson 和 Zave：需求描述的是世界，不是机器 |
| 改了意思留下记录 | lock、声明过的差异、rationale record | Doorstop 的指纹和 suspect link、Architecture Decision Records |
| 规模大了不乱 | charter、topic、local，特别法优于一般法 | 立法文本的组织方式 |

也有反面的教训。有的工具从标题生成 ID，标题一改，ID 就跟着变，所以 Skopo 的 key 绝不从文本里算出来。今天的 spec-driven 工具，比如 GitHub 的 Spec Kit，大多从一份新写的 spec 出发，生成计划和代码；spec 写完以后怎么跟着系统一起演进、第三个月怎么不漂，不是它们的重点，却正是 Skopo 想回答的。

那为什么不干脆造一种更精确的语言？这条路也有人走过。形式化方法（Z、Alloy、TLA+）足够精确，机器也能验证，可做决定的人读不懂，更别说写了。反过来，vibe coding 的 prompt 人人都写得出，却用完就扔。我们的选择是：句子仍然是人话，规矩套在外面。

### 4.2 现状：为什么是现在，走到了哪一步

那为什么是现在？这些零件大多已经有十几、二十年的历史，之前很少有人把它们拼在一起用，是因为太贵：把每条规则写成 statement、让它和代码保持一致、在两者分叉时发现分叉，全都要靠人。agent 改变了这一点，它能从意图写出代码，也能从代码读回意图，而且便宜。可 agent 这个翻译器并不可靠，它会读错，也会漏。这恰好是这些规矩存在的另一个理由：agent 写出来的东西得能被检查，得有人逐条拍板，人接受的版本得记下来。规矩越清楚，一个不可靠的翻译器就越用得起。

再说现状。Skopo Specification 0.1.0 还是草案，还没有正式发布。三层、statement 和它的 key、加粗的关键词、lock 和声明过的差异，这些核心我们预计不会再变；别的部分还会随着大家的使用调整。规范的附录 D 列出了已知的缺口，比如 lock 只记下被接受的原文，还不记录是谁接受了哪一条。照着它已经能写出一个独立的检查器；对生成器的要求大多没法从输出验证，一组一致性测试也还没有，这些欢迎一起补。我们写的检查器和 Claude Code 插件只是一个参考实现。

想看一份完整的 skopo，可以看 Skopo 自己的。我们让插件从开发 Skopo 的仓库恢复出一份 skopo，描述规范、参考工具、插件和这份白皮书的页面，29 分钟写出 334 条 statement，列出 33 个问题，其中大约 20 个是规范和工具里实实在在的毛病；没有这次运行，大部分会带进第一个版本。修完之后，我们又手动让 agent 拿改过的规范去对照这份 skopo，它报告了 40 条对不上、18 条缺的、1 条该删，我们核对之后才改进去，所以现在这份 skopo 有 350 多条，不是 334 条。这一次先动的是规范，skopo 跟在后面，正是 §2.4 说的那种对照。这份 skopo 和规范放在同一个 repo 里，现在还是草稿：还没有人逐条接受过它，所以它没有 lock。

还没试过的，比试过的多：

- 从一份 PRD 或者 feature spec 写起，而不是从代码恢复；
- 让 skopo 跟着代码保持一致：每次 merge 时对照，还是定期对照，该问什么、问多少；
- 让 agent 以 skopo 为出发点写代码；
- 人逐条看几百条 statement 要花多久，会不会变成成批点头，恢复出来的 statement 到底有多少是对的；
- 在规则不那么密集的系统上，它还有多大用处。我们认为 Skopo 最适合金融、人事、合规这类规则密集的系统；体验驱动的产品，“世界”很薄，skopo 也会薄到没什么可读。

### 4.3 愿景：梯子上的下一级

软件开发的历史，就是沿着一架抽象的梯子往上爬。每上一级，人就从一类细节里解放出来；而每一级都靠一个翻译器，把上面写的可靠地翻成下面的。

| 这一级 | 把人从什么里解放出来 | 靠什么翻译到下一级 |
|---|---|---|
| 机器码 | （起点） | — |
| 汇编 | 记 opcode | assembler |
| 高级语言 | 管寄存器和内存 | compiler |
| 声明式语言（SQL） | 想数据怎么取 | query planner |
| 框架和托管运行时 | 搭底层基础设施 | runtime、framework |
| 意图（Skopo，这一级） | 逐行写代码、读代码 | coding agent（双向） |

某一级一旦有了可靠的翻译器，下面那一级慢慢就没人日常去读了。agent 在哪里变得可靠，哪里的代码就开始变成汇编。梯子上也有几级横档没搭上去：COBOL、4GL、MDA、no-code，它们造的都是“更像人话的语言”，翻译器又窄又漏，也没有一条路能把代码读回意图。这一次不同：翻译器是双向的，而我们也不再造新语言。

> [!FIGURE] fig-ladder · 抽象的梯子，和没搭上去的横档
> 自下而上五级：机器码、汇编、高级语言、声明式语言（SQL）、框架和托管运行时；最上面是虚线的一级"意图（Skopo）"。
> 每一级左侧标"把人从什么里解放出来"，右侧标"靠什么翻译到下一级"，文字照搬正文的表格（机器码一行是起点，两侧留空）。每两级之间画一个向下的翻译箭头。
> 最上一级和下面之间的翻译器标"coding agent（双向）"：一支向下的箭头，一支向上的箭头，都用虚线，因为这一级还在搭。
> 梯子旁边画四根断掉的、半透明的横档：COBOL、4GL、MDA、no-code。它们伸向"意图"这一级，但够不着。
> 不要画年份，不要画人物。

我们希望 Skopo 就是这一级；说得具体一点，是让每个系统的 skopo 成为 agentic coding 的出发点。今天，agent 进到一个 repo，先读的是 AGENTS.md、CLAUDE.md 这类文件，里面有约定、有命令、有注意事项，却没有“这个系统应该是什么样”。我们设想的是，agent 从 skopo 出发：一次改动先是一份意图的 diff，再落到代码上；人 review 的是意图，让代码和意图对得上是 agent 的活。当然，这还是愿景。至少在未来一年里，代码还在，人也还会去读它，skopo 和代码会一起存在。

再往远看，会过去的是那套受控的写法：加粗的关键词、一个元素一条 statement、机械的 lint。我们估计它是一座大约两年的桥，等模型能稳定地直接读 prose，这些约束就没有必要了。会留下来的，是人决定过的规则、形态决定、设计决定和例子，是每一条的身份和 lock，以及将来要补上的、谁在什么时候接受了哪一条的记录。更长的上下文让“读”变得免费，却不会让“决定”变得免费。

> [!BET]
> 长期来看，一切都会变成 wishful coding。你只需要说出什么应该为真，实现它的系统会被生成、运行、替换，没有人需要再去看它；界面、运行平台这些形态，也都会被抽象掉，变得无感。上面的论证并不依赖这个赌注。

> [!FIGURE] fig-lifespan · 写法会过去，内容会留下
> 横轴是时间，从"今天"到"长期"，不标具体年份。
> 这三条带子不是层，不要用四层的颜色：内容和记录用强调色，受控的写法用中性灰，代码用 code 的底色。
> 上方一条带子标"受控的写法（加粗关键词、一个元素一条、lint）"，在大约两年处淡出，标"我们估计：一座两年的桥"。
> 中间一条带子标"内容和记录（人决定过的规则、形态决定、设计决定、例子、ID、lock，以及将来的接受记录）"，一直延续到最右端。
> 下方一条带子标"代码"：前段是实线，标"至少一年和 skopo 并存"，之后逐渐变淡，最右端标"wishful coding"。

### 4.4 下一步

Skopo 现在最需要的，是更多人来用、来挑毛病。

规范、参考工具和 Skopo 自己的 skopo 都在 [github.com/57blocks/skopo](https://github.com/57blocks/skopo)：规范从 [`rfc/drafts/0.1.0.md`](https://github.com/57blocks/skopo/blob/main/rfc/drafts/0.1.0.md) 读起，Skopo 自己的 skopo 在 [`skopo/`](https://github.com/57blocks/skopo/tree/main/skopo)。照着规范，你可以写自己的检查器或生成器，也可以写给别的 coding agent 用的插件。

想动手试的话，最快的办法是在 Claude Code 里装上我们的插件：

```bash
claude plugin marketplace add 57blocks/skopo
claude plugin install skopo@skopo
```

然后在要描述的 repo 里运行 `/skopo:init`。它会读代码和文档，写出一份 skopo 草稿，再附一份问题清单，列出代码和文档对不上的地方。草稿只是提议，插件不会替你写 lock；等你和团队看过、接受了，再用 `/skopo:lock` 写下第一版。`/skopo:lint` 随时可以检查一份 skopo 合不合规。不用 Claude Code 的话，检查器也能单独运行，只要 Node.js 22 以上，不用装依赖：在 repo 里跑 `node tools/cli/lint.mjs <skopository 的路径>`。

我们做过的那些实验，运行记录没有放进公开的 repo，因为里面有试点系统自己的材料；§4.2 那次描述 Skopo 自己的运行，结果就是 repo 里的 `skopo/`。想看实验记录的话，欢迎联系作者：[teki@57blocks.com](mailto:teki@57blocks.com)。试过之后，也请告诉我们哪条规矩不好用，哪里说不通。
