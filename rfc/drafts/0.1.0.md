## Abstract

A skopository is a repository of intent documentation for a software system: what must be true
about the system, what form it takes for the people who use it, and how it is designed. It sits
one level of abstraction above the code and is read and written by people and agents alike. This
document specifies the files of a skopository, the form and identity of its statements, the lock
that records them, and the checks that decide whether a skopository conforms, so that independent
tools can write, read and check skopositories.

## Status of this document

This document is a draft of version 0.1.0, the first version of the specification. It may change
until it is published; a published version is never edited, and a correction or a change appears in
a later version (section 14).

This version is an early release. Before 1.0.0 any minor version may change any requirement
(section 14.1), and later 0.x versions are expected to. The core of the model is expected to hold:
the layers, statements with their anchors, kinds and keys, bold normative keywords, refinements, and
the lock with its declared differences. Other parts may change as skopositories are written and
used. Appendix D lists the known gaps of this version.

## 1. Introduction

### 1.1 Purpose

Code says what a system does. A skopository says what the system is for and what has been decided
about it, in words that hold whatever realizes them. It is a companion of the code: it lives beside
the source tree for as long as the code lives, for new systems and old ones alike.

This specification fixes the structure precisely enough that a skopository written by one tool can
be checked by another, and that a person can read any skopository without learning a tool.

### 1.2 Scope

In scope: the files of a skopository, the syntax and meaning of statements, statement identity,
the lock, translations, the checks, and what a tool that writes a skopository must guarantee.

Out of scope: how changes to a skopository are reviewed and merged, how a code change is compared
with a skopository, how a skopository is recovered from code beyond the guarantees in section 13,
and where discussions, questions and plans are kept. Such processes may be specified separately.

### 1.3 Conformance classes

| Class | Conforms when |
|---|---|
| Skopository | it meets every MUST and MUST NOT in sections 3 to 11 that applies to it, and a conforming checker reports no error for it |
| Checker | it performs every check in section 12.1 with the stated severity, and reports an error exactly when section 12.1 says so; the semantic checks of section 12.2 are optional |
| Generator | it writes only conforming skopositories, and meets section 13 |

A skopository that does not follow a SHOULD still conforms; a checker MAY report the departure as a
warning. A checker MAY stop after errors that would make every later finding meaningless (a
language with no dictionary entry, placeholders left in the files), provided it says that it
stopped.

Some requirements are judged rather than checked: where a statement belongs (section 3.2), whether
a statement in the spec leaks form (section 6.4), and what a statement means. A checker reports what
words can show. A skopository it passes can still break a judged requirement, and review is what
catches that. Of the requirements on generators, only those on what a generator writes can be
verified from its output (section 13).

## 2. Conventions and terminology

### 2.1 Requirement keywords

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, NOT
RECOMMENDED, MAY and OPTIONAL in this document are to be interpreted as described in BCP 14
(RFC 2119, RFC 8174) when, and only when, they appear in all capitals, as shown here.

These key words state requirements on skopositories and tools. They are distinct from the
normative keywords written inside a skopository (section 6), which are lowercase and bold, such as
`**must**`, and which state requirements on the system the skopository describes.

### 2.2 Terms

| Term | Meaning |
|---|---|
| skopository | a directory that conforms to this specification; informally, a system's "skopo" |
| statement | one Markdown element that carries an anchor; the unit of identity, review and checking |
| element | a paragraph, a list item, a block quote, a table row, or a whole list, table or quote (section 5.1) |
| anchor | a caret followed by an ID at the end of an element: `^R-k3m9pq` |
| ID | a kind letter, a hyphen and a key: `R-k3m9pq` |
| key | the six random characters of an ID; a statement's identity |
| kind | what a statement is: term, act, rule, assumption, example, form decision or design decision (section 5.4) |
| layer | one of the spec, the product bindings and the tech bindings (section 3.1) |
| product | anything built from the system that has its own consumers |
| consumer | a person or system that uses a product: a user, an integrator, an operator who runs it |
| developer | a person who builds or maintains a product |
| connective text | any element without an anchor |
| link | an ID inside the parentheses that may follow an anchor (section 5.5) |
| refinement | a rule that narrows another rule within a scope and applies instead of it there |
| statement file | a Markdown file under `spec/`, `bindings/product/`, `bindings/tech/` or `views/` |
| lock | the file `spec.lock.json` (section 10) |
| fingerprint | the hash of a statement's text (section 10.2) |
| rationale record | a file under `rationale/` that declares changes and may give their reasons (section 9) |
| view | a document generated from a skopository for one kind of reader, such as a handbook, a test plan or a translation; of all views, a skopository stores only translations (section 11) |
| translation | a view that renders statement files of the spec or the bindings in another language, stored under `views/<language>/` (section 11) |
| checker | a tool that checks a skopository against section 12 |
| generator | a tool that writes a skopository, from code or from anything else (section 13) |

### 2.3 Text format

Every file of a skopository is UTF-8 without a byte order mark, with LF line endings. Markdown
files follow CommonMark 0.31.2 with the table extension of GitHub Flavored Markdown. Section 5.1
restricts which Markdown constructs may appear in statement files.

## 3. The model

### 3.1 Three layers

A skopository describes a system in three layers. Each holds one kind of content and answers to
one test.

| Layer | Location | Holds | Kinds |
|---|---|---|---|
| Spec | `spec/` | what must be true in the world the system serves | T, A, R, W, E |
| Product binding | `bindings/product/<product>.md` | what the product's consumers see and rely on | F |
| Tech binding | `bindings/tech/<product>.md` | what only the product's developers see, at the level of design | D |

Code is a fourth level below the tech binding. It is not part of a skopository.

### 3.2 Placement

Authors and generators MUST place each statement in the layer its content belongs to. Placement is
judged, not mechanical; the following tests decide it, in this order:

1. If an outside party (a client, a partner, a regulator, a standard published by a body outside
   the system's makers) would object to changing it, it belongs in the spec.
2. If it would stay true were the whole system replaced by people working with pen and paper, it
   belongs in the spec.
3. If a change to it would be noticed by the product's consumers and by nobody outside the product,
   it belongs in the product binding.
4. If a change to it would be noticed by the product's developers and by nobody else, and it is a
   decision of design (how the product is divided into components, where its data is kept, how the
   components talk to each other, what each may reach) that would still hold were the code
   rewritten to the same design, it belongs in the tech binding.
5. Otherwise it is code or a coding convention, and does not belong in the skopository.

Where a product is itself an interface (an API, a file format), the parts its consumers use belong
in the product binding. An interface that only the makers' own applications use belongs in the
tech binding.

A statement in the spec that holds only for some forms of the system is a declared leak: it MUST
begin with the bold form condition (section 6.4).

### 3.3 Products

A product has one product binding and at most one tech binding, with the same file name. A tech
binding MUST NOT exist without its product binding. A system that is offered as software
others run and also run by its makers for their own users is two products.

### 3.4 References point up

A layer MUST cite only statements of its own layer or of the layers above it (section 7.2): the
spec cites the spec; a product binding cites the spec and product bindings; a tech binding cites
all three. A skopository MUST NOT cite code: no statement file names a file, module, symbol or
line of the code (section 7.3). Code MAY cite a skopository by ID; how it does so (a comment, a
commit message trailer) is left to tools.

### 3.5 What a skopository does not hold

A statement file MUST NOT contain status, progress, plans, assignees, open questions, discussions,
meeting notes or changelogs. A skopository SHOULD NOT contain guides, how-to material or onboarding
pages. These belong to the tools a team uses for its work. Views for readers are generated from a
skopository when needed and are not stored in it; translations are the exception (section 11).

A skopository MUST NOT contain secrets, credentials or personal data, and MUST NOT contain the name
of a person; it refers to people by role. These requirements are judged (section 1.3): no check can
find every secret, and section 15 says why they matter.

## 4. Repository layout

### 4.1 Root

A skopository is a directory. It MAY be a directory inside a code repository (conventionally
`skopo/`) or a repository of its own. Its root holds:

| Path | Presence | Holds |
|---|---|---|
| `skopo.json` | REQUIRED | the manifest (section 4.2) |
| `keywords.json` | REQUIRED | the normative keyword dictionary (section 6.1) |
| `README.md` | REQUIRED | what the skopository describes and how to read it |
| `spec/` | REQUIRED | statement files of the spec |
| `bindings/product/` | OPTIONAL | one statement file per product |
| `bindings/tech/` | OPTIONAL | one statement file per product |
| `rationale/` | OPTIONAL | rationale records |
| `views/<language>/` | OPTIONAL | translations of the spec and the bindings |
| `spec.lock.json` | RECOMMENDED | the lock; absent until the first one is written |

Other files and directories MAY exist at the root; checkers ignore them.

### 4.2 Manifest

`skopo.json` is a JSON object with one REQUIRED member:

| Member | Type | Meaning |
|---|---|---|
| `specVersion` | string | the version of this specification the skopository follows, as `MAJOR.MINOR.PATCH` |

Other members are reserved for later versions and MUST be ignored by tools that do not know them.

### 4.3 The spec directory

`spec/` holds any number of statement files, in any number of subdirectories. The following
arrangement is RECOMMENDED:

| Path | Holds |
|---|---|
| `spec/<shared>.md` | words every domain uses |
| `spec/<domain>/charter.md` | a domain's words and its principles |
| `spec/<domain>/<topic>.md` | detailed rules of the domain; they refine the charter's principles |
| `spec/<domain>.md` | a small domain in one file |
| `spec/local/<jurisdiction>.md` | rules of one office, market, regulator or operator among several; they refine the general rules |

A domain SHOULD be cut where a word changes meaning. A topic file SHOULD be readable in one sitting.

### 4.4 Bindings

`bindings/product/` and `bindings/tech/` MUST NOT contain subdirectories. A binding's file name
without `.md` names its product.

### 4.5 Front matter

A statement file MAY begin with a front matter block: a line `---`, lines of YAML, and a line `---`.
Its member `language` gives the language of the file as a BCP 47 tag; without it, the language is
`en`. The language selects the entry of the keyword dictionary used for the file, and that entry
MUST exist. Other members are ignored.

## 5. Statements

### 5.1 Elements

A statement file is read as a sequence of elements separated by blank lines. Lines are classified
by their first non-space characters:

| Line starts with | Element |
|---|---|
| `#` | heading; always connective text |
| `\|` | table |
| `>` | block quote |
| `-`, `*` or a number and `.`, followed by a space | list item |
| anything else | paragraph |

Consecutive non-blank lines of the same element form one element, with one exception: a list
continues through non-blank lines that start no other element, which belong to the list item
before them. Each list item, at any indentation, is an element of its own; a whole list is also an
element (section 5.3).

A statement file MUST NOT contain fenced code blocks, HTML blocks, footnote definitions or link
reference definitions. Inline Markdown (emphasis, code spans, links) MAY appear anywhere.

Text inside a code span is quoted, not used. A bold normative keyword in a code span carries no
force, and an ID, an anchor or a placeholder in one cites nothing and defines nothing, so a
statement can quote the syntax of a skopository. A code location stays a code location in a code
span (section 7.3).

### 5.2 Anchors

A statement is an element whose text ends with exactly one anchor, optionally followed by one link
group (section 5.5):

```
- A job **must not** take its verdict from another job. ^R-kgpmb6
- A verification **must** compare against the Wasm deployed now. ^R-ajnbap (refines R-5bc5gf)
```

An anchor is `^` followed by an ID (section 8.1). It SHOULD be separated from the text before it by
white space. An element MUST NOT contain an anchor anywhere but at the end of its text, and MUST NOT
end with more than one anchor.

### 5.3 Element forms

A paragraph, a list item or a block quote is a statement when it ends with an anchor.

A whole list, table or block quote is one statement when the paragraph that immediately follows it
consists of an anchor alone, optionally followed by a link group. Such a lone anchor MUST follow a
list, a table or a block quote, and the element it follows MUST NOT contain anchors of its own.

A table row is a statement when its first cell holds exactly one ID, without a caret. A table that
holds such rows MUST be preceded immediately by a paragraph without an anchor that ends with a
colon (`:`, or the full-width `：`). That paragraph is the stem. It is part of every row's statement
and is not connective text, so a bold normative keyword in it binds every row. Rows whose first
cell holds no ID (the header row, the delimiter row) are not statements. A table row cannot carry
links; a statement that needs links is written as a list item.

```
Retention periods:

| ID | Data | Kept for |
|---|---|---|
| R-21hxfq | a job never published | 30 days |
```

### 5.4 Kinds

| Kind | Letter | Is | Lives in |
|---|---|---|---|
| term | T | the meaning of a word; the defined word is bold | spec |
| act | A | something someone does, and what follows from it | spec |
| rule | R | what must, must not or may happen, or a definition of a state | spec |
| assumption | W | something true of the world that the system relies on and does not enforce | spec |
| example | E | a concrete scenario that shows what a rule makes true | spec |
| form decision | F | a decision about what the product's consumers see | product binding |
| design decision | D | a decision about how the product is built | tech binding |

A statement of kind F MUST be in a product binding, and a product binding MUST contain only
statements of kind F. A statement of kind D MUST be in a tech binding, and a tech binding MUST
contain only statements of kind D. Statements in `spec/` MUST be of kinds T, A, R, W or E.

### 5.5 Links

A link group is a pair of parentheses after the anchor, holding IDs separated by commas:

| Statement kind | Link group | Means |
|---|---|---|
| E | `(R-…, T-…)` | the statements the example checks |
| F, D | `(R-…, F-…)` | the statements the decision serves, of the kinds its file may cite (section 7.2) |
| R | `(refines R-…)` | the rules this rule refines |

A statement of kind T, A or W MUST NOT carry a link group. The link group of a rule MUST begin with
`refines`, and a rule MUST refine only rules.
A refining rule applies instead of the rule it refines, within the scope of its file. Links obey the
direction of section 7.2.

### 5.6 Statement text

The text of a statement is computed as follows, and is what the lock fingerprints:

1. Take the lines of the element. For a lone-anchor statement, take the lines of the element it
   follows.
2. From each line, remove leading white space and one leading list marker (`-`, `*` or a number
   and `.`, followed by white space) or quote marker (`>`), with the white space after it.
3. Join the lines with single spaces.
4. Remove the trailing anchor and link group, or the lone-anchor paragraph.
5. Replace every run of white space with one space, and trim both ends.

For a table row, the text is the stem's text, one space, and the row's cells after the first, joined
by ` | `. Each cell is taken with every run of white space replaced by one space and both ends
trimmed. The first cell holds the ID and is not part of the text, so re-aligning a table's columns or
moving its rows changes no row's text. The row in section 5.3 has the text
`Retention periods: a job never published | 30 days`.

### 5.7 Connective text

Elements without anchors, and all headings, are connective text, except a table stem (section 5.3).
Connective text carries no force: it MUST NOT contain a bold normative keyword (section 6).

## 6. Normative keywords

### 6.1 The keyword dictionary

`keywords.json` is a JSON object. Each member whose name does not begin with `_` is keyed by a
language tag and holds:

| Member | Type | Presence | Meaning |
|---|---|---|---|
| `requirement` | array of strings | REQUIRED | keywords of obligation, e.g. `must` |
| `prohibition` | array of strings | REQUIRED | keywords of prohibition, e.g. `must not` |
| `permission` | array of strings | REQUIRED | keywords of permission, e.g. `may` |
| `formCondition` | array of strings | OPTIONAL | words that open a form-conditional rule, e.g. `Where` |
| `hiddenForce` | array of strings | OPTIONAL | words that express force without a keyword, e.g. `cannot` |
| `warnUnbolded` | boolean | OPTIONAL | whether the language has word boundaries, so that a plain keyword can be found |

Members whose names begin with `_` are comments. A checker MAY supply a default for a member that a
language entry lacks, from the dictionary in appendix B; the skopository's own entries always win.

### 6.2 Force

A normative keyword carries force only when it is bold: `**must**`, `**must not**`, `**may**`. When
keywords overlap, the longest match applies (`**must not**` is a prohibition, not a requirement).

Bold normative keywords MAY appear only in statements of kinds R, F and D. Statements of kinds T, A,
W and E MUST NOT contain them.

A rule that contains a bold normative keyword is behavioral. A rule without one is definitional: it
says what a word or a state means, and MUST NOT state an obligation, a prohibition or a permission
in other words ("cannot", "is refused", "never"). Every obligation, prohibition or permission in a
rule, a form decision or a design decision SHOULD carry a bold keyword.

### 6.3 Plain keywords

A keyword written without bold inside a statement of kind R, F or D is ambiguous. Authors SHOULD
bold it when it is normative and reword it when it is not.

### 6.4 Form conditions

A rule in the spec that holds only for some forms of the system MUST begin with a bold form
condition word: `**Where** a submitter uses the console, the terms **must** be shown first.` Such a
rule is a declared leak of form into the spec. A form condition word that is not bold has no
meaning.

### 6.5 Granularity

A statement SHOULD hold one thing a reviewer would accept or reject. A statement with more than
three bold normative keywords SHOULD be split.

## 7. References and layers

### 7.1 Resolution

Every ID that appears in a statement file or a rationale record MUST be the ID of a statement
defined in the skopository, with the kind that statement has now. The exception is an ID in a
`Retires` field of a rationale record, and an ID elsewhere in a rationale record whose key is
retired (section 8.5).

### 7.2 Direction

| A statement file in | MAY cite kinds |
|---|---|
| `spec/` | T, A, R, W, E |
| `bindings/product/` | T, A, R, W, E, F |
| `bindings/tech/` | T, A, R, W, E, F, D |

### 7.3 Code locations

A statement file MUST NOT name a location in code. A checker detects at least these forms:

- a path of two or more segments ending in a source or infrastructure file extension
  (`ts`, `tsx`, `js`, `mjs`, `cjs`, `go`, `rs`, `py`, `java`, `kt`, `rb`, `swift`, `tf`, `hcl`,
  `prisma`, `sql`, `sh`);
- a file name with such an extension followed by a colon and an identifier (`file.ts:resolve`).

A bare file name that is a word of the world (`build.rs`, `Node.js`) is not a code location. Paths
to directories and configuration keys cannot be told from other text mechanically; review catches
them.

## 8. Identity

### 8.1 Syntax

```
id   = kind "-" key
kind = "T" / "A" / "R" / "W" / "E" / "F" / "D"
key  = 6 char
char = DIGIT / %x61-68 / %x6A-6B / %x6D-6E / %x70-74 / %x76-7A
     ; 0-9 a-h j k m n p-t v-z: Crockford base32, lowercase
```

An ID is recognized only when the character after it is not a lowercase letter or a digit.

### 8.2 Assignment

A tool that assigns a key MUST choose it at random, uniformly, from the 32^6 possible keys, and MUST
NOT derive it from the statement's text, location or kind. Before assigning a key, it MUST check that
no statement in the skopository, no entry in the lock and no retired key uses it. These requirements
bind tools; a checker cannot tell how a key was chosen.

### 8.3 Identity and kind

A statement's identity is its key. When a statement moves between layers, its kind letter changes
and its key stays. Every citation MUST then use the new letter (section 7.1).

### 8.4 Uniqueness

A key MUST be defined at most once across `spec/`, `bindings/product/` and `bindings/tech/`. Views
reuse the keys of the statements they translate.

### 8.5 Retirement

A key is retired when a rationale record lists it under `Retires`. A retired key MUST NOT be
defined again, for any statement. Removing a statement that the lock holds MUST be declared by
retiring its key (section 10.3).

### 8.6 Placeholders

A generator MAY use temporary placeholders while writing. A conforming skopository MUST NOT contain
a token of the form kind, `-@`, and a label (`R-@fresh-wasm`).

## 9. Rationale records

A rationale record declares changes to statements and MAY say why they were made. Records are
OPTIONAL: a skopository needs one only to declare differences from the lock (section 10.3).

A record is a Markdown file `rationale/<YYYY-MM-DD>-<slug>.md`, where the date is the day of the
decision. Its first heading is its title. It holds a two-column table whose rows are fields:

| Field | Holds |
|---|---|
| `Touches` | IDs of statements whose meaning this change sets or changes, including new ones |
| `Rewords` | IDs of statements whose wording changed without a change of meaning |
| `Retires` | IDs of statements this change removes |
| `Sources` | where the decision or its reason is recorded |
| `Grade` | `evidenced` when a source states the reason; `inferred` when the reason is a reading of several sources |
| `Recorded` | when and how the record was made |

A field MAY be omitted. A field row is a table row whose first cell is the field name; IDs in a
field are separated by commas or spaces. The body after the table MAY give the reason. A record
MUST NOT be needed to understand any statement.

A rationale record is history, not a layer: it MAY name sources of any kind, including code. It
names code by file, symbol or commit, not by line number, since lines move (check L7).

## 10. The lock

### 10.1 Format

`spec.lock.json` is a JSON object:

| Member | Type | Holds |
|---|---|---|
| `records` | array of strings | the file names of the rationale records already folded into the lock |
| `statements` | object | one member per statement in `spec/` and `bindings/`, keyed by key |
| `translations` | object | one member per translation directory (section 11), keyed by its path |

Each member of `statements` is an object with `kind` (the kind letter), `where` (the file path
relative to the root, a colon and a line number), `sha` (the fingerprint) and `text` (the statement
text). Members appear in ascending order of key. `where` is informative and plays no part in
identity. Each member of `translations` maps keys to objects with `sha` (the fingerprint of the
translated text) and `source` (the fingerprint of the source statement when the translation was
locked, or null).

### 10.2 Fingerprint

The fingerprint of a statement is the first 16 hexadecimal digits, lowercase, of the SHA-256 hash
of its text (section 5.6) encoded in UTF-8.

### 10.3 Declared differences

When a lock exists, every difference between it and the skopository MUST be declared by a rationale
record whose file name is not yet in the lock's `records`:

| Difference | Declared under |
|---|---|
| a statement absent from the lock | `Touches` |
| a statement whose kind differs from the lock | `Touches` |
| a statement whose fingerprint differs from the lock | `Touches` when its meaning changed, `Rewords` when only its wording did |
| a statement in the lock that is no longer defined | `Retires` |

### 10.4 Writing the lock

The lock is written when people first accept a skopository, and rewritten after each change they
accept. Rewriting it adds the names of all current rationale records to `records`. Because the lock
records acceptance, a tool writes it only when people accept, never on its own (section 13).

The lock records the text of each statement as it was accepted. It does not record who accepted a
statement or when; the skopository's version control holds that (appendix D).

## 11. Translations

A translation renders statement files of the spec and of the bindings in another language. It is
the only view a skopository stores, because a translation, like its source, is read and accepted by
people. It lives in `views/<language>/`, mirrors the paths of the files it translates (so a
translated binding lives under `views/<language>/bindings/`), and MUST declare its language in
front matter; it MAY cover only some of those files. A translation is a statement file: the
requirements of sections 5 to 8 apply to it, and it cites as the layer of its source does.

A translated statement MUST carry the anchor of the statement it translates. Its kind MUST equal the
source's kind, and a translated rule, form decision or design decision MUST carry the same classes
of force (requirement, prohibition, permission) as its source. A translation MUST NOT define a key
that the spec and the bindings do not define. Translations are OPTIONAL.

## 12. Checks

### 12.1 The checks

A conforming checker performs the following checks. An error makes the skopository
non-conforming. A warning reports something a person should look at. A report is information.

| Check | Requirement | Severity |
|---|---|---|
| L0 | `skopo.json` exists and declares a `specVersion` the checker supports (section 14.3) | error |
| L0 | `keywords.json` and `README.md` exist, and the dictionary has an entry for every language a statement file declares | error |
| L1 | no placeholders remain (section 8.6) | error |
| L1 | anchors are well formed, end their element, and an element ends with at most one anchor | error |
| L1 | lone anchors and tables of statements follow section 5.3 | error |
| L1 | statement files contain none of the constructs section 5.1 excludes | error |
| L1 | no key is defined twice, and no retired key is defined | error |
| L1 | kinds F and D live in their bindings, and the bindings hold nothing else | error |
| L2 | every cited ID resolves with its current kind (section 7.1) | error |
| L2 | link groups appear only where section 5.5 allows them; only rules refine, and they refine only rules | error |
| L3 | a spec statement that names a form, outside a form-conditional rule, is reported as a possible undeclared leak | warning |
| L4 | the number of rules with and without an example | report |
| L5 | citations point up (section 7.2) | error |
| L5 | no statement file names a code location (section 7.3) | error |
| L5 | every tech binding has a product binding with the same name, and the binding directories hold no subdirectories | error |
| L7 | no line in a statement file begins with a status field (`Status:`, in any case, bold or not), and no statement file or rationale record holds a line citation (a file name, a colon and a line number) | error |
| L8 | no bold normative keyword in connective text | error |
| L9 | no bold normative keyword in a statement of kind T, A, W or E | error |
| L9 | a rule without a bold keyword uses a word from the dictionary's `hiddenForce` | warning |
| L9 | a plain keyword in a statement of kind R, F or D, or in a table stem | warning |
| L9 | a statement with more than three bold normative keywords | warning |
| L10 | every difference from the lock is declared (section 10.3) | error |
| L10 | a statement whose meaning changed is cited by examples, refinements or bindings that need re-checking | warning |
| L11 | translations declare their language, and keep keys, kinds and forces (section 11) | error |

Checks L1, L2, L5, L7 and L8 apply to translations as to every statement file. L6 is not used:
earlier drafts used it for a check that was dropped, and the number stays free so that check names
keep their meaning across versions. L3 is a warning because whether a statement leaks form is
judged (section 3.2); an example that checks only form-conditional rules may name the form it is
about. Its words that name a form are a checker's own list; the
reference checker's list for English is: screen, page, button, click, checkbox, dropdown, popup,
tooltip, form field, endpoint, api, database, cron, server, url, json, login, email, e-mail, slack,
sms, push notification, app, mobile, web, ui, dashboard, phone, message.

### 12.2 Semantic checks

A checker MAY also use a language model for checks that words cannot decide. Their findings are
warnings, never errors.

| Check | Requirement |
|---|---|
| S1 | a statement declared under `Rewords` kept its meaning |
| S2 | a translation kept the meaning of its source |
| S3 | no statement file names code in a form section 7.3 cannot detect (a directory, a configuration key) |

### 12.3 Output

A checker MUST report each finding with its check, its severity and the file it concerns, with the
line wherever the finding concerns one, and MUST signal failure (for a command-line tool, a non-zero
exit status) when it reports an error. The format of the report is not specified.

## 13. Generators

A generator writes a skopository from sources: code, documents, or people's answers. A conforming
generator:

1. MUST write a skopository that a conforming checker reports no error for, with `skopo.json`,
   `keywords.json` and `README.md`.
2. MUST NOT leave placeholders in it.
3. MUST rest every statement on a source a reader could open, and MUST NOT state as intent what no
   source supports.
4. MUST NOT write into the skopository the disagreements it finds between sources, its questions,
   or its own notes. It SHOULD report them to the people it works for, outside the skopository.
5. When sources disagree, SHOULD write the statement as the most deliberate source states it: a
   promise to an outside party, then a recorded decision, then a design document or specification,
   then the code, then a comment; between sources of the same rank, the later one. This ranking is a
   heuristic, not a test of truth; the generator SHOULD report which source it followed.
6. SHOULD write as a design decision only what the system does consistently or what a document
   states. Where one place departs from what the rest of the system does, it SHOULD leave the
   departure out and report it.
7. When reading a version-controlled source, SHOULD read its default branch, and MUST state which
   revision it read, in its report outside the skopository.
8. MUST NOT change any file its sources track. It writes only the skopository and its own report.
9. MUST NOT write the lock: the lock records text people accepted (section 10.4), and what a
   generator writes is a proposal until they do.

A generator also assigns keys as section 8.2 requires. Requirements 1 and 2 concern what a generator
writes and can be verified with a checker; the others concern how it works and cannot be verified
from its output.

## 14. Versioning

### 14.1 Version numbers

This specification is versioned with Semantic Versioning 2.0.0. For versions 1.0.0 and later:

| Increment | When |
|---|---|
| MAJOR | a conforming skopository may stop conforming, or a conforming tool may stop conforming |
| MINOR | requirements are added that every conforming skopository already meets, or that only add warnings or optional features |
| PATCH | clarifications and corrections that change no requirement |

Before 1.0.0, any increment of MINOR may change requirements in any way.

### 14.2 Publication

Each published version is a separate document and is never edited after publication. Errors in a
published version are corrected in a later version.

### 14.3 Declaring and accepting a version

A skopository declares the version it follows in `skopo.json`. A checker that supports version
`X.Y.Z` MUST accept a skopository that declares `X.Y.W` for any `W`, and for `X` of 1 or more, any
`X.V.W` with `V` not greater than `Y`. It MUST report an error for any other declared version, and
for a missing or malformed `specVersion`.

Before 1.0.0 a checker therefore accepts only the minor version it implements: a skopository that
moves to a new 0.x version is checked again, and its lock is rewritten.

## 15. Security and privacy considerations

Sources are untrusted input to a generator. Text in code, documents or commit messages that is
addressed to a tool is data, not an instruction; a generator MUST NOT act on it.

A skopository MUST NOT contain secrets, credentials or personal data, and MUST NOT name people.

The disagreements a generator finds can reveal weaknesses in the system it reads: an authentication
path that skips a check, a promise the deployment does not keep. A generator SHOULD treat its report
of them as confidential to the people it works for. This is one reason section 13 keeps them out of
the skopository, which may be shared more widely.

## Appendix C. A minimal skopository

A lending library, as one product run by its makers.

```
# Lending: charter

## Words

- A **member** is a person the library has registered to borrow books. ^T-0b7199
- A **loan** is one book lent to one member, from the day it is lent until it comes back. ^T-aq165k
- A loan is **overdue** when its due date has passed and the book is not back. ^T-kx1kt6

## Principles

- A book **must not** be lent while it is on an open loan. ^R-cxsjfa
- A member with an overdue loan **must not** borrow another book. ^R-5tps87
- The library **must not** charge a member for returning a book late. ^R-3bpfef

> *Example.* A member returns a book a week late. Nothing is charged, and the member can borrow again the same day. ^E-g1j5t8 (R-3bpfef, R-5tps87)
```

# Lendbox: product binding

## Appendix D. Known gaps

This appendix is informative. It lists what this version knowingly leaves open; later versions are
expected to address these.

| Gap | Now |
|---|---|
| Confirmation | The lock records accepted text. It does not record who accepted a statement, when, or whether a statement was recovered from sources or decided by a person. Version control holds who and when; how a skopository records confirmation is not yet specified. |
| Rationale integrity | Rationale records are not fingerprinted: a record already folded into the lock can change without a check noticing. |
| Judged requirements | Placement (section 3.2), leaks of form (section 6.4) and meaning are judged, not checked. The word lists behind L3 and `hiddenForce` are heuristics and report false positives. |
| Generators | Most requirements on generators (section 13) cannot be verified from what a generator writes, and its ranking of sources is a heuristic. |
| Conformance tests | There is no suite of test skopositories with expected checker findings yet; appendix C is the only complete example. |
| Edges of the syntax | Whole-list, whole-table and whole-quote statements, table-row statements and placeholders have seen little use and may change. |
| Code citations | How code cites a skopository is left to tools. |
